# پروفایل تحصیلی دانش‌آموز — سیاست و رفتار

> **سیاست محصول قطعی:** دانش‌آموز به‌تنهایی مالک انتخاب و تغییر پایه، شاخه، زمینه و رشتهٔ خودش است. **هیچ مرحلهٔ تأیید مدیریتی در این جریان وجود ندارد** (نه pending approval، نه admin approval، نه awaiting administrator).

## ۱) API

| متد | مسیر | کار |
|---|---|---|
| GET | `/api/v1/account/academic-profile` | پروفایل فعلی + گزینه‌های انتخاب‌گر (پایه‌ها، شاخه‌ها، زمینه‌ها، رشته‌ها) + mirror |
| PUT | `/api/v1/account/academic-profile` | ذخیرهٔ فوری انتخاب با اعتبارسنجی سمت سرور |

- احراز هویت با `require_student` موجود؛ CSRF/RBAC از middlewareهای مشترک.
- ownership: فقط پروفایل خود کاربر تغییر می‌کند — endpoint هرگز user_id را از بدنه نمی‌پذیرد.
- `user.role` در این API **غیرقابل‌دستکاری** است (فیلد در مدل بدنه وجود ندارد و سرویس آن را نمی‌نویسد).

## ۲) بدنهٔ PUT

```json
{ "grade_number": 10, "branch_code": "technical_vocational", "ground_code": "services", "field_code": "tec-services-حسابداری" }
```

## ۳) قواعد اعتبارسنجی سمت سرور (پیام‌ها فارسی)

1. پایه باید ۱–۱۲ باشد؛ در غیر این صورت «پایهٔ تحصیلی نامعتبر است.»
2. پایه‌های ۱ تا ۹: هر شاخه/زمینه/رشته ارسالی → «پایه‌های ۱ تا ۹ شاخه، زمینه و رشته ندارند؛ فقط پایه را انتخاب کن.»
3. پایه‌های ۱۰ تا ۱۲ بدون شاخه → «برای پایه‌های دهم تا دوازدهم انتخاب شاخه (نظری، فنی‌وحرفه‌ای، کاردانش) الزامی است.»
4. شاخه باید بازهٔ پایه را پوشش دهد.
5. نظری: زمینه ممنوع («در شاخهٔ نظری زمینه وجود ندارد…») و رشته باید متعلق به شاخهٔ نظری باشد.
6. فنی‌وحرفه‌ای/کاردانش: اول زمینه («ابتدا زمینهٔ تحصیلی… را انتخاب کن.») سپس رشتهٔ متعلق به همان زمینه («این رشته به زمینهٔ انتخاب‌شده تعلق ندارد.»).

ترتیب UI نیز همین است: پایه ← شاخه ← زمینه (فقط هنرستانی) ← رشته ← ذخیره؛ گزینه‌های نامعتبر اصلاً نمایش داده نمی‌شوند.

## ۴) ذخیره و اثر فوری

- Upsert در `student_academic_profiles` + همگام‌سازی mirrorهای قدیمی در همان تراکنش: `users.grade_level = پایه` و `users.major = code رشته (یا NULL)`.
- هیچ reload لازم نیست؛ پاسخ PUT بلافاصله پروفایل جدید را برمی‌گرداند و callback فرانت state پایه/شاخه/رشتهٔ جاری را به‌روز می‌کند → **درخواست بعدی معلم خصوصی از پایه/رشتهٔ جدید استفاده می‌کند.**
- فیلتر سخت پایه (`enforce_student_grade_level`) دست‌نخورده باقی است: کتاب بالاتر از پایهٔ پروفایل همچنان 422 می‌شود؛ فقط پیام خطای «پروفایل ناقص» فارسی و خود-خدمتی شده است («ابتدا پایهٔ تحصیلی خود را در پروفایل انتخاب کن.»).
- RAG per-request و stateless است (فیلتر Qdrant لحظهٔ پرسش ساخته می‌شود)؛ بنابراین ترکیب محتوای پایهٔ قبلی و جدید از مبنا ممکن نیست و cache وابسته به پایه وجود ندارد که نیاز به invalidation دستی داشته باشد. گفت‌وگوهای تاریخی با پایهٔ خودِ آن جلسه حفظ می‌شوند و حذف/ترکیب نمی‌شوند.

## ۵) پنل مدیریت (فقط مشاهده)

در پاسخ `GET /api/v1/admin/users/{id}` کلید جدید `academic_profile` شامل: پایه، دوره، شاخه، زمینه، رشته، سال تحصیلی و تاریخ آخرین تغییر (`updated_at`). هیچ دکمهٔ تأیید/رد/فعال‌سازی پایه به این بخش اضافه نشده است.

> نکتهٔ شفاف برای مالک: endpointهای مدیریتیِ از قبل موجود ویرایش `grade_level` (فاز RBAC قبلی) حذف نشدند، چون خط قرمز «هیچ قابلیت فعلی حذف نشود» را می‌شکند؛ اما هیچ جریان تأیید جدیدی هم اضافه نشده و نمایش پروفایل در پروندهٔ دانش‌آموز صرفاً read-only است. تصمیم نهایی دربارهٔ حذف/بقا آن endpointها با مالک است (بند ریسک‌های گزارش).

## ۶) رفتار پایه‌های ۱ تا ۹

انتخاب دوره و پایه فقط؛ هیچ فیلد شاخه/رشته/زمینه در UI رندر نمی‌شود و ارسالشان از API هم رد می‌شود.

## ۷) تغییر پایه و دامنهٔ بازیابی

- پایهٔ جدید = منبع رسمی همهٔ درخواست‌های بعدی؛ فیلترهای موجود (grade_number در فیلتر Qdrant + سقف پایه) بدون تغییر باقی می‌مانند.
- پروفایل‌های موجود بدون دلیل بازنویسی نمی‌شوند؛ فقط وقتی دانش‌آموز خودش ذخیره کند تغییر می‌کنند.
